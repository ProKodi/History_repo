# Структурное проектирование как инженерная парадигма

Структурное проектирование возникло как ответ на «кризис сложности» программирования 1960–1970-х годов. Его главная цель — сделать разработку управляемой за счет:

* декомпозиции,
* формализации,
* модульности,
* иерархического управления сложностью.

Главная идея:

> сложную систему невозможно понять целиком, поэтому ее необходимо разложить на функциональные уровни.

В центре структурного подхода находится **функция**, а не данные.

---

# Ключевые принципы структурного проектирования

## 1. Абстракция

Абстракция позволяет рассматривать систему по уровням детализации.

На верхнем уровне:

* описывается назначение системы;

На нижнем:

* конкретные алгоритмы и процедуры.

Это позволяет:

* анализировать архитектуру до реализации;
* локализовать ошибки проектирования;
* уменьшать когнитивную нагрузку.

---

## 2. Декомпозиция («разделяй и властвуй»)

Система разбивается на:

* подсистемы,
* модули,
* процедуры.

Каждый модуль:

* решает одну задачу;
* имеет четкую ответственность;
* минимально зависит от остальных.

Это приводит к:

* независимому тестированию;
* параллельной разработке;
* повторному использованию.

---

## 3. Иерархия

Структурный подход использует нисходящее проектирование (Top-Down Design):

```text
Система
 ├── Подсистема A
 │    ├── Модуль A1
 │    └── Модуль A2
 └── Подсистема B
```

Каждый уровень:

* уточняет предыдущий;
* сохраняет логическую связность.

---

## 4. Формализация

Формальные модели:

* устраняют неоднозначность;
* обеспечивают верификацию;
* делают архитектуру воспроизводимой.

Именно отсюда появились:

* DFD,
* SADT/IDEF0,
* структурные карты,
* псевдокод,
* спецификации процессов.

---

# Связность и зацепление

Это центральные метрики качества архитектуры.

## High Cohesion (высокая связность)

Модуль должен:

* выполнять одну функцию;
* иметь единую цель.

Пример:

* модуль авторизации;
* модуль расчета зарплаты.

---

## Low Coupling (низкое зацепление)

Модули должны:

* минимально знать друг о друге;
* взаимодействовать через интерфейсы.

Чем слабее зависимость:

* тем проще сопровождение;
* тем легче изменения.

---

# Методы структурного проектирования

## 1. Data Flow Design (DFD)

Основная идея:

> система — это преобразователь потоков данных.

Ключевые элементы:

| Элемент          | Назначение          |
| ---------------- | ------------------- |
| Процесс          | Преобразование      |
| Поток данных     | Передача информации |
| Хранилище        | Сохранение          |
| Внешняя сущность | Источник/получатель |

DFD особенно эффективны для:

* учетных систем,
* документооборота,
* банковских процессов.

---

# Методология Джексона (JSD)

JSD делает акцент:

* не на функциях,
* а на поведении объектов во времени.

Главная особенность:

* моделирование жизненного цикла сущностей.

Подходит для:

* систем реального времени,
* промышленных систем,
* телекоммуникаций.

---

# Метод Варнье–Орра

Главный принцип:

> структура программы должна соответствовать структуре данных.

Основа:

* иерархия данных;
* вложенность;
* последовательности;
* повторения.

Метод особенно полезен:

* при генерации отчетов;
* обработке документов;
* пакетных вычислениях.

---

# Методология SADT / IDEF0

SADT — одна из самых влиятельных системных методологий.

Ее особенность:

* моделирование функций через ICOM-интерфейсы.

---

# Концепция ICOM

Каждая функция имеет 4 типа взаимодействий:

| Тип       | Назначение        |
| --------- | ----------------- |
| Input     | Что преобразуется |
| Control   | Что управляет     |
| Output    | Результат         |
| Mechanism | Чем выполняется   |

---

## Визуальная модель SADT

```text
           Control
              ↓
Input → [ Функция ] → Output
              ↑
          Mechanism
```

---

# Почему SADT оказался революционным

До SADT:

* процессы и данные смешивались хаотично.

SADT впервые:

* отделил управление от преобразования;
* ввел строгую декомпозицию;
* стандартизировал описание процессов.

---

# Иерархия SADT

SADT использует строгую декомпозицию:

```text
A-0  — система целиком
A0   — основные подсистемы
A1   — детализация подсистемы
A11  — детализация процесса
```

---

# Правило 3–6 блоков

Каждая диаграмма:

* должна содержать 3–6 функций.

Причина:

* ограничения человеческого восприятия.

Слишком много блоков:

* разрушает читаемость модели.

---

# Организационная ценность SADT

SADT — не только нотация.

Это:

* процесс коллективного согласования;
* инструмент коммуникации;
* средство управления знаниями.

Особенно важен цикл:

* автор → эксперт → корректировка.

---

# Переход к объектно-ориентированному подходу

Структурный подход оказался недостаточным для:

* GUI;
* распределенных систем;
* сложных предметных областей;
* постоянно меняющихся требований.

Возникла новая парадигма:

> моделировать не функции, а сущности реального мира.

---

# Объектно-ориентированная декомпозиция

В ООП центральной сущностью становится объект.

Объект:

* хранит состояние;
* содержит поведение;
* взаимодействует сообщениями.

---

# Три свойства объекта

| Свойство     | Смысл        |
| ------------ | ------------ |
| Идентичность | Уникальность |
| Состояние    | Данные       |
| Поведение    | Методы       |

---

# Класс как шаблон

Класс определяет:

* структуру данных;
* методы;
* интерфейс взаимодействия.

Объект — экземпляр класса.

---

# Ключевые принципы ООП

## Инкапсуляция

Скрытие внутренней реализации.

Преимущество:

* изменение внутреннего кода не ломает систему.

---

## Наследование

Повторное использование поведения.

```text
Транспорт
 ├── Автомобиль
 └── Самолет
```

---

## Полиморфизм

Один интерфейс — разные реализации.

Например:

```python
shape.draw()
```

может:

* рисовать круг;
* квадрат;
* треугольник.

---

# Главное различие структурного и объектного подходов

| Структурный                         | Объектный                |
| ----------------------------------- | ------------------------ |
| Центр — функции                     | Центр — объекты          |
| Алгоритмы первичны                  | Данные и поведение едины |
| Top-Down                            | Часто Bottom-Up          |
| Слабая связь данных и процедур      | Инкапсуляция             |
| Сложно сопровождать большие системы | Высокая расширяемость    |

---

# Когда структурный подход лучше

Структурное проектирование по-прежнему эффективно для:

* встроенных систем;
* драйверов;
* компиляторов;
* математических вычислений;
* систем с жесткими алгоритмами.

---

# Когда лучше ООП

ООП особенно эффективно для:

* корпоративных систем;
* GUI;
* веб-платформ;
* ERP/CRM;
* распределенных систем;
* долгоживущих продуктов.

---

# Современная инженерная практика

Сегодня почти все крупные системы используют гибридный подход:

* архитектурно — объектная модель;
* алгоритмически — структурные методы;
* процессно — Agile/Scrum/MSF;
* аналитически — UML/C4/IDEF0.

---

# Главный исторический итог

Структурное проектирование стало первым действительно инженерным подходом к созданию ПО.

Именно оно:

* ввело дисциплину декомпозиции;
* породило архитектурное мышление;
* сформировало культуру формального анализа;
* подготовило основу для появления UML, ООП и современных архитектурных практик.

Объектно-ориентированный подход не отменил структурный — он расширил его, сместив акцент:

* от функций к моделированию предметной области,
* от процедур к взаимодействующим сущностям,
* от алгоритмов к архитектуре изменений.
