# UML и объектно-ориентированное моделирование: системная структура

## 1. Место UML в жизненном цикле разработки

Объектно-ориентированный подход делит разработку на две взаимосвязанные стадии:

| Этап                           | Назначение                | Основной вопрос                 |
| ------------------------------ | ------------------------- | ------------------------------- |
| Object-Oriented Analysis (OOA) | Анализ предметной области | «Что должна делать система?»    |
| Object-Oriented Design (OOD)   | Проектирование реализации | «Как система будет это делать?» |

UML выступает универсальным языком визуализации этих этапов.

---

# 2. Основные принципы ООП

## Абстракция

Выделение только значимых характеристик объекта.

Пример:

* «Транспорт» → скорость, грузоподъемность
* скрываются детали двигателя

## Инкапсуляция

Объединение данных и методов внутри объекта.

### Цели:

* защита состояния;
* контроль доступа;
* локализация изменений.

## Наследование

Создание иерархий классов.

Пример:

```text
Транспорт
   ├── Автомобиль
   ├── Самолет
   └── Корабль
```

## Полиморфизм

Одинаковый интерфейс — разные реализации.

Пример:

```text
draw()
```

у:

* Circle
* Square
* Triangle

реализуется по-разному.

# 3. UML: категории диаграмм

## Структурные диаграммы

Описывают статическое устройство системы.

### Основные:

* диаграмма классов;
* диаграмма компонентов;
* диаграмма пакетов;
* диаграмма развертывания.

## Поведенческие диаграммы

Показывают динамику и взаимодействия.

### Основные:

* диаграмма вариантов использования;
* диаграмма деятельности;
* диаграмма состояний;
* диаграмма последовательности.

---

# 4. Диаграмма классов (Class Diagram)

## Назначение

Описание:

* классов;
* атрибутов;
* методов;
* связей между объектами.

---

## Структура класса

```text
-------------------------
|       Student         |
-------------------------
| -name: String         |
| -group: String        |
-------------------------
| +calculateGPA(): int  |
-------------------------
```

### Секции:

1. Имя класса
2. Атрибуты
3. Методы

---

# 5. Видимость элементов

| Символ | Тип доступа | Значение               |
| ------ | ----------- | ---------------------- |
| +      | public      | доступен всем          |
| -      | private     | доступен только классу |
| #      | protected   | доступен наследникам   |
| ~      | package     | доступ внутри пакета   |

---

# 6. Отношения между классами

## Ассоциация

Обычная связь между объектами.

```text
Student —— Course
```

---

## Агрегация

«Часть может существовать отдельно».

```text
University ◇—— Student
```

Полый ромб.

---

## Композиция

«Часть не существует без целого».

```text
House ◆—— Room
```

Закрашенный ромб.

---

## Наследование (Generalization)

```text
Vehicle
   ▲
   |
Car
```

---

## Реализация интерфейса

```text
Interface
   △⋯⋯
     |
Class
```

---

## Зависимость

Слабая временная связь.

```text
Client - - - > Service
```

---

# 7. Кратность связей

| Обозначение | Значение         |
| ----------- | ---------------- |
| 1           | ровно один       |
| 0..1        | ноль или один    |
| *           | любое количество |
| 1..*        | минимум один     |
| n..m        | диапазон         |

Пример:

```text
Teacher 1 —— * Student
```

---

# 8. Диаграмма вариантов использования (Use Case)

## Назначение

Описание функциональных требований с точки зрения пользователя.

---

## Основные элементы

### Актор

Внешняя роль.

Примеры:

* Клиент;
* Администратор;
* Платежная система.

---

### Вариант использования

Функция системы.

Примеры:

* «Оформить заказ»;
* «Авторизоваться».

---

## Системная граница

Прямоугольник, определяющий:

* что входит в систему;
* что относится к внешнему окружению.

---

# 9. Связи в Use Case Diagram

## Association

Связь актора и функции.

---

## include

Обязательное включение общего поведения.

```text
Оформить заказ
      |
   <<include>>
      |
Проверить оплату
```

---

## extend

Опциональное расширение поведения.

```text
Оплатить заказ
      |
   <<extend>>
      |
Использовать бонусы
```

---

## Generalization

Наследование ролей или сценариев.

---

# 10. Различие include и extend

| include                 | extend                   |
| ----------------------- | ------------------------ |
| всегда выполняется      | выполняется условно      |
| повторное использование | вариативность            |
| обязательная часть      | дополнительное поведение |

---

# 12. Типичные ошибки UML

## На диаграммах классов

* путаница агрегации и композиции;
* чрезмерная детализация;
* монолитные схемы;
* циклические зависимости.

## На диаграммах вариантов использования

* смешение include и extend;
* моделирование интерфейса вместо требований;
* отсутствие системной границы.

---

# 13. Ключевая идея объектного подхода

Главное отличие от процедурного проектирования:

| Процедурный подход          | Объектный подход                     |
| --------------------------- | ------------------------------------ |
| функции обрабатывают данные | объекты владеют данными и поведением |
| логика централизована       | ответственность распределена         |
| высокая связность           | модульность и инкапсуляция           |

---

# 14. Методологический вывод

Объектно-ориентированное моделирование позволяет:

* уменьшать сложность систем;
* локализовать изменения;
* повторно использовать компоненты;
* формализовать архитектуру;
* обеспечивать прослеживаемость требований.

Диаграммы UML при этом выступают не просто документацией, а инструментом инженерного мышления, связывающим:

* требования,
* архитектуру,
* проектирование,
* реализацию,
* сопровождение ПО.
